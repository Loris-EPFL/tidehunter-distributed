# Distributed write-durability tiers

Code: `tidehunter/src/distributed/durability/` (`mod.rs`, `frontier.rs`, `native.rs`, `synchronous.rs`, `tests.rs`). Code for durable-prefix recovery: `tidehunter/src/distributed/remote_db/durable_cut.rs`.
`ReceiptDurability` is an in-memory label. Durable-prefix recovery adds one coordinator file (`durable-cut.v1`, see [Native recovery](#native-recovery-durable-prefix)). It also adds the owner `DurableProgress` request. The wire tag is frozen in `tidehunter/src/distributed/tcp/wire_tag_tests.rs`.

## Decision

Distributed Tidehunter offers two write-acknowledgement tiers. `native` is the contract of native Tidehunter: page-cache acknowledgement. It is the default in the engine (`DurabilityConfig::default`), in the kv-research adapter, and in the comparison campaign (`cloud_campaign.DEFAULT_DURABILITY_TIER`). The campaign uses it when a job or spec names no tier. `synchronous` is the stricter option. It stays available and unchanged when you select it explicitly. Reviewed campaign specs that were generated with the earlier synchronous matrix default name it explicitly.

The tiers have this crash-loss difference. After an owner kernel crash or power loss, `native` can lose acknowledged batches above the owner's synced frontier. `synchronous` loses no acknowledged batch. The failure matrix gives the details. Both tiers use one frontier tracker and one syncer for each owner WAL. They differ only in the acknowledgement condition.

| | `native` (default) | `synchronous` |
|---|---|---|
| Config label (`DurabilityTier::as_str`) | `native` | `synchronous` |
| Receipt label (`ReceiptDurability::as_str`) | `appended` | `synced` |
| Acknowledgement condition | owner **appended** frontier covers the batch | owner **synced** frontier covers the batch |
| Waits for fsync | no | yes (group commit) |
| Background fsync | yes, native cadence: when an owner WAL fragment is finalized (appended frontier crosses a fragment boundary), no age bound by default; immediately when requested | same syncer; every acknowledgement is a trigger when requested |
| Explicit flush | `native::flush`, `frontier::flush_all` | same; returns immediately when nothing is unsynced |
| Matched benchmark cohort (`comparison_cohort`) | `native_pagecache` | `value_wal_barrier_and_valkey_appendfsync_always` |

Native source of the `native` contract: Tidehunter paper §3.1 and §5 (`papers/parsed/Tidehunter-2026-v2.md`). The writer allocates a WAL position. It copies the data into the mmap WAL (page cache). It updates the index. It completes without a wait for fsync. A tracker advances the highest WAL offset below which every entry is processed. A syncer batches fsyncs. Durability against an application crash is immediate. Durability against a kernel crash needs the fsync. Applications that need more call an explicit flush.

## Frontiers

Positions are byte offsets in the owner WAL. A completed range is `[start, end)`. A frontier is an exclusive end.

* **Appended frontier** (`Frontier::appended`): the highest offset below which every position is completely written. Writers complete in any order (`Frontier::complete(start, end, batches)`). A completion that does not start at the frontier waits in a sorted, bounded buffer until the gap before it closes. Callers that already serialize appends use `publish_appended(end, batches)`. This frontier is the paper tracker.
* **Synced frontier** (`Frontier::synced`): the highest offset below which every position is durable. Only the syncer advances it, after its fsync callback returned `Ok`.
* **Syncer** (`Syncer::spawn`): one thread for each owner WAL. It captures the whole appended frontier. It calls `sync(end)` once, without any lock. Then it publishes the synced frontier and wakes the waiters. Every batch that completed during the fsync is covered by the next call. Group commit needs no per-request queue.
* **Cadence** (`SyncPolicy`, default `SyncPolicy::native(fragment_bytes)`): the syncer runs when the appended frontier is past a fragment boundary above the synced frontier. Native Tidehunter syncs a WAL map when it is finalized (paper §3.1, no other trigger). `fragment_bytes` is the owner storage `fragment_bytes`. Pass it to `DurabilityConfig::frontier_config(start, fragment_bytes)`. The syncer also runs immediately when any waiter exists. `max_unsynced_age_ms: Option<u64>` (config key `max_unsynced_age_ms`, default `None`) is an opt-in extra sync trigger. It is stronger than native. It is not a guaranteed bound (see the failure matrix). It is not part of the native-matched contract. A run that sets it is not a native-matched run and must say so.
* **Waiters** block on condition variables. `wait_appended` is the Native acknowledgement. `wait_synced` is the Synchronous acknowledgement; it raises demand so the syncer starts immediately. `request_sync` + `wait_flush` is the flush.
* **Flush**: `native::flush(frontier, deadline)` takes the appended frontier at the call. It requests a sync of that frontier. It waits until the synced frontier reaches it. It therefore covers everything acknowledged before the call.
* **`flush_all(owners, deadline)`**: it starts a flush on every owner (`FlushTarget::begin_flush`). Then it waits for all of them against one deadline (`finish_flush`). The fsyncs run in parallel on the owner syncers. The report has one result for each owner. One failing owner does not hide the others. The coordinator implements `FlushTarget` for a remote owner client. Begin means send the request. Finish means await the reply.

## Recovery invariant

> The stored control region of the coordinator index must name only positions inside each owner's **synced** frontier, or batches that the durable cut records as aborted.

Reason. A stored region lets recovery skip WAL replay below it. Assume that a region names an appended-but-unsynced batch. Assume also that the owner then loses that batch in a kernel crash. The index then points at bytes that do not exist. This is the `AcknowledgeBeforeBarrier` fault of `group_model.rs`, moved from the acknowledgement to the stored region. The rule holds for both tiers. A Native acknowledgement can be ahead of the synced frontier, but a stored region cannot.

**Capture rule.** The snapshot cadence has no age bound. The lag of the region therefore has no bound. The snapshot pass (`hybrid/snapshot.rs`) stores a region only up to the persisted version B durable cut. The durable-cut actor syncs every owner and fsyncs its `durable-cut.v1` record before the pass runs. In release mode, the pass proves that the head of the region is at or below that cut. A head above the cut is a version B defect. The pass then stores nothing and returns `Invalid`. The pass never cuts at a synced frontier that it read earlier without a new request.

How code enforces it. `Frontier::synced()` is a lock-free `Acquire` read of an owner-local offset. The syncer stores that offset with `Release` after the fsync returned. Offsets from different owners are not comparable. Their minimum is not a logical cut. The coordinator expresses the cut in batch versions. Batch versions order all owners. An owner that seals a file also does an `fdatasync` and a directory sync first (see `ARCHITECTURE.md` section 5). Tests: `seeded_crash_model_checkpoints_reference_only_synced_positions` and `concurrent_writers_keep_acknowledgements_and_checkpoints_behind_the_device`. The first test uses 300 seeds. The device persists before the frontier publishes. The crash discards unsynced bytes. A control that cuts at the appended frontier must violate the rule, so the check is not vacuous.

## Native recovery: durable prefix

Config: `RemoteDatabaseConfig::durable_cut` (`DurableCutConfig`: `lag_ms` default 1000, `lag_bytes` default 64 MiB; absent means the defaults). Recovery is always the durable prefix with the extend rule. The `per_owner` and `strict` options are removed designs (tag `archive/multi-design-*`).

Problem. One native WAL loses at most a suffix after a power loss (paper §3.1). With one WAL for each owner, each owner can lose a different suffix. Per-owner recovery can keep `{x=2}` (version 1, owner B, synced) and lose `{x=1, y=1}` (version 0, owner A, unsynced). The recovered state is then not a state that the database ever had.

Contract (`durable_prefix`). Recovery keeps an exact prefix of the coordinator version order. The prefix contains every batch at or below the persisted cut. It also contains every batch that an explicit flush (`flush_durable`) covered when that flush returned. A power loss of any owner loses at most a suffix of that order. Batches above the cut can be lost even if they were acknowledged and survived on their owner. This is the Native acknowledgement contract (page cache, not fsync).

Mechanism.

* **Cut.** For the serving epoch, `cut = min(published floor, synced end of every owner that holds a receipted batch not covered by its last report)`. The published floor is the exclusive contiguous publication frontier. Aborted versions below it count as covered. An owner is idle when its last report covers all its receipted batches. An idle owner does not pin the cut. The minimum is O(owners). It runs at report cadence on the actor thread, not on the write path. The write path stores one atomic for each receipt group and one for each publication call.
* **Progress.** One poller thread for each owner (`value-wal-durable-{partition}`) uses its own plain connection (counted in `NON_READ_CONNECTIONS`). While its owner holds uncovered receipts, the poller long-polls `DurableProgress`. The wait is `min(lag_ms / 4, 5 s)`. The owner replies after each durable advance or at the wait. The coordinator does not poll an idle owner. `synced` in the reply covers every batch of the stream at or below it (data, namespace and live root synced). On a live NVMe-oF stream, the reply covers only the prefix of the installed strict live root (`synced_end` is the root's end). Recovery rejects a corrupt frame only below that root. Beyond it, recovery stops at the first defect like at a torn tail. A syncer barrier that defers the root inside a fragment therefore reports nothing. The next root install reports everything it covers. The triggers for that install are a fragment crossing, flush, fence, shutdown or nudge. A seal bounds the report the same way. Recovery rejects a scan that ends below the sealed end.
* **Progress wait.** The poller's connection is a dedicated progress lane (`Client::connect_progress_shared`). Neither end spins while a poll is parked. The poller waits in `poll(2)` on these events: transport readiness, its stop eventfd and the request deadline. Transport readiness is the socket on TCP. On OFI verbs it is the provider CQ wait fd armed by `fi_trywait`, plus the TCP control socket for peer loss. The owner session waits only while the parked poll is its sole work. It waits on the same transport readiness, on a per-session eventfd, on the listener's shutdown eventfd and on the request deadline. The durable-progress completion path signals the per-session eventfd after it publishes the reply. The signals are: immediate reply, nudge error, worker panic, full or stopped hub, fence or seal retirement, hub stop. A wake never counts as durability. Every wake only starts another sweep. An OFI endpoint without a CQ wait fd fails the lane at connect, before the Status handshake, with `durable progress wait unavailable: …`. Software RxM is one such endpoint, and a provider that refuses `FI_WAIT_FD` is another. An owner whose OFI endpoint has no CQ wait fd refuses each poll before control admission. It sends a correlated `Response::Error` that carries the same prefix and keeps the session open. The coordinator then does not mistake it for peer loss. The poller of a lane that reports this error stops instead of reconnecting. A lost capability after setup (a fatal `fi_trywait` or wait error) is a transport error of the session. No wire message, protocol number or persisted format changes. An alternate TCP progress endpoint for OFI routes without a wait fd is not provided.
* **Nudge.** The actor (`value-wal-durable-cut`) keeps bounded samples of the published floor. The oldest floor above the cut is `lag_ms` old, or `lag_bytes` were appended above the cut. In either case, the actor asks every lagging owner to sync at its next poll (`sync = true`). A lagging owner has uncovered receipts and a synced end below the floor. The owner self-adopts a leased extent first. The actor issues at most one nudge for each `lag_ms` to each owner. The first nudge of the epoch is sent immediately. A report does not re-arm it. Without this bound, a lagging peer that prevents the cut from advancing keeps both triggers true. An appending owner would then be nudged once for each poll round trip. On a live stream, the owner then runs one barrier on the request worker. It syncs everything appended and installs the strict root over it. Then it replies at once. The poller takes a nudge at its next poll start, which can be up to `lag_ms / 4` late. Two nudge installs can therefore occur a few milliseconds apart. Over any window T, a pinned owner takes at most ⌈T/lag_ms⌉ + 1 nudge root installs (temp write, fsync, rename, directory fsync). These installs do not run on the acknowledgement path. A failed poll re-sends the same nudge after a `lag_ms` back-off. On another stream, the owner's syncer runs the sync. The nudge is a sync trigger, not a hard bound. The poll in flight (up to `lag_ms / 4`), the per-owner interval and the fsync add to the lag.
* **Record.** `durable-cut.v1` in the authority directory: CRC-framed YAML (`format: 2`, `database`, `live: {epoch, next}`, `owners: [{partition, incarnation, synced_next}]`, `truncations: [{epoch, next}]`). The install sequence is temp file, fsync, rename, directory fsync. The file name stays fixed across formats. A record of another format therefore fails the open instead of reading as absent. `live` names the tracked epoch and its persisted cut. Only the actor rewrites it while the database serves, and only when the cut moved. `owners` holds one continuity mark for each owner of the tracked epoch: the owner's incarnation at the epoch's fence and its highest reported synced end. The marks are written with the cut, so they can lag the reports. A lagging mark only lowers the continuity bound. A report with another incarnation zeroes the mark's incarnation. `flush_durable` sends the flushed prefix to the actor and returns after the record covers it.
* **Owner continuity.** The owner creates its incarnation once at open: 128 random bits from the OS generator, never persisted and never zero. It returns the incarnation in `NodeStatus::incarnation` and in every `DurableProgressReport`. Every owner process restart and every reboot opens again, so the incarnation changes. A restarted owner is never continuous, on the same boot too. After a writeback error the kernel can drop the dirty pages. The old process saw the error and stopped. Nothing outside that process proves the loss. `NodeStatus::recovery_clean` is false when a WAL recovery that this incarnation ran ended early at a lost, torn or invalid frame and a later fragment still starts with a valid frame. This is a hole below the recovered tail. The recovery that this incarnation ran can be at open or at a live fence. `recovery_clean` is also false, until the owner process restarts, once this incarnation saw a persistence failure or a reader poison. A reader poison is a failed log frontier or either poison funnel. It includes a recoverable live failure that a later live fence recovered in-process. A damaged or unwritten frame at the very tail is the normal crash tail and keeps the flag clean. Frames after a defect inside the same fragment cannot be located without a scan of user bytes for magic. The code therefore probes only later fragments. An owner is continuous when its fence `incarnation` equals its mark and `recovery_clean` is true. It is then the same owner process that appended, with no failed sync, so it lost nothing it appended. A coordinator-only crash keeps every owner continuous. The continuity bound is the minimum recorded `synced_next` over the owners that are not continuous. It is unbounded when all are continuous. It is 0 when an owner has no mark. A possible later improvement, not implemented: the coordinator verifies continuity for an owner-only restart while the coordinator stays up.
* **Restart durability guard.** After a writeback error the kernel can also leave pages clean with content that never reached the device. A restarted process reads those frames. A later fsync then succeeds because nothing is dirty. A WAL-replay recovery of an unsealed stream therefore writes back every frame and skip marker that it accepts above the persisted root position. It writes them from the bytes that it validated. The root position is `partition-wal-root-v1` `synced_end`, or the live frontier root. The write of a frame is `CrcFrame::new(payload)` (the checked length and checksum). The write of a skip marker is its header and checked zeros. Recovery syncs each written file before any root, seal or barrier. No byte is read again, so a page evicted after validation cannot change what becomes durable. Any write or sync error fails the recovery, and the owner stops. Cost: one write and fsync of the uncheckpointed suffix above the root position for each recovery. The cost is never on the write path (`storage/wal_replay/recovered_suffix.rs`).
* **Recovery.** For the previously tracked epoch, the bound starts at `max(live.next, stored-region cut + 1)`. Recovery keeps the run of surviving sequences from the bound. A missing sequence below the continuity bound was never written. It was an aborted version, or a version that never reached a continuous owner. The run skips it. A missing sequence at or above the bound may have been lost by an owner that is not continuous. The run stops there. Fencing synced every surviving batch, so the run is durable. The result is still an exact prefix. Recovery appends `{epoch, next}` to `truncations`. It persists the record before the new epoch activates, so a discarded batch never returns. Every open honours every recorded truncation. Each tracked fencing generation has at most one entry. The open that trims a fencing generation removes its entry only after every owner acknowledged the trim. The list is therefore bounded by the retained fencing generations. The new tracked epoch starts with one mark for each fenced owner (its fence incarnation, `synced_next = 0`).
* **Scope.** An epoch is tracked when every owner reports the `native` tier at fence time. Synchronous owners are per-batch durable and are never truncated. WAL replay is the only history. The removed `on_disk` receipt history and `per_owner` recovery are archived designs.
* **Stats.** `RemoteDatabase::durable_cut_stats()`: `enabled`, `persisted_next`, `reports`, `nudges`, `persists`, `persist_failures`, `poll_failures`, `certifications`. `RecoveryStats`: `cut_discarded_batches`, `cut_extended_batches`, `cut_skipped_versions`, `cut_continuity_bound`, `recovered_cut`. A failed record write is counted and retried at the next evaluation. The record then lags, which only makes recovery keep less.
* **Shutdown.** The service stops after the shutdown checkpoint. Stop signals each poller's stop eventfd. A parked poll then ends immediately without a failed-poll reconnect. The poller closes its session and is joined. Owner shutdown signals the listener's shutdown eventfd before it joins the sessions.

## Failure matrix

`Appended` = in the owner page cache with every earlier batch. `Synced` = covered by a completed fsync. Rows for the owner assume that the owner WAL is a local file. The NVMe-oF row covers the live path, where the owner writes the WAL through an NVMe-oF initiator.

| Failure | `native` | `synchronous` |
|---|---|---|
| Owner process crash (kernel up) | Every acknowledged batch survives in the page cache and is recovered. The frontiers restart at the recovered end. This is the same as native Tidehunter. Local WAL: recovery replays the tail above the last durable root. Live NVMe-oF WAL (`storage.rs`): recovery scans strictly below the persisted live frontier root as before. Beyond it, recovery adopts complete valid frames and stops quietly at the first missing or invalid frame. It then installs a new root before the history root advances. The Native live acknowledgement requires the contiguous appended frontier, so no acknowledged frame lies beyond a hole. The live root is written by persistence barriers: the syncer (at a fragment crossing), flush, fence/retire, shutdown and the durable-progress nudge. The restart durability guard makes the adopted suffix durable before the recovery syncs it. With `durable_prefix`, the restarted owner is not continuous. Recovery keeps the durable cut prefix. Acknowledged batches beyond it can be discarded at the first missing version at or above the continuity bound. That version is an aborted version or a version lost to a writeback error. Writeback errors never break the prefix. Tests: `storage/tests/live_native.rs`, `remote_db/durable_cut_tests.rs`. | Same, and every acknowledged batch is also below the root. |
| Owner kernel crash or power loss | Batches above the synced frontier can be lost, although they were acknowledged. The window is everything above the synced frontier. The fragment trigger and the opt-in age trigger decide when the syncer *starts* an fsync. Neither trigger is a hard bound on the loss window. The syncer cannot interrupt an fsync in flight. Scheduling delay, I/O delay or a stalled fsync therefore lets acknowledged writes accumulate past one fragment or past the age. No backpressure limits that. In normal operation the unsynced suffix is about one fragment, as in native Tidehunter, which has the same property. The stored control region never references those batches (invariant), so recovery is consistent, not complete. With `durable_prefix` the loss is a suffix of the coordinator version order. Batches of other owners above the first lost version are discarded too. | No acknowledged batch is lost. |
| Coordinator crash | Owner WALs hold every acknowledged batch. Recovery loads the last stored control region (synced batches only). It replays the owner streams in batch-version order from the offsets that the region names. Replay has no length limit. `durable_prefix` + `extend` has two cases. Case 1: every owner process kept running, saw no persistence failure and recovered without a hole. The code then keeps every surviving batch and skips a missing version (aborted or unwritten). Case 2: one of these conditions is false, for example an owner process also restarted. A missing version at or above the continuity bound then stops the run. An acknowledged batch above it is discarded unless the persisted cut or a flush covered it. A kernel crash of an owner at the same time loses its unsynced tail as above. | No acknowledgement can lie above the synced frontier, so nothing is ever truncated at the cut. |
| NVMe-oF target crash or target host kernel crash (live WAL path) | The initiator write completion and the target page cache (`buffered_io=1`) are not durability. Batches not yet covered by the owner's persist barrier can be lost. Reads of the sealed and live route fail until the target restarts and the owner fences and recovers. [INFERENCE: loss window equals the owner's unsynced window; it depends on the barrier reaching the target backing file, see `experiments/nvmeof/LIVE_WAL.md`.] | A receipt exists only after the barrier that LIVE_WAL.md requires, so acknowledged batches survive. |
| Coordinator-to-owner connection break (owner process alive, same incarnation, lease valid) | The coordinator reconnects. It probes the owner's adopted prefix. It rewrites the unadopted suffix with identical bytes at identical offsets. It re-declares adoption. A frame is acknowledged at the same point as before (owner page cache). A rewrite that cannot complete fails the database as today. The unacknowledged suffix is then replayed or truncated at the first invalid frame. | Same, and every resent frame carries FUA exactly as its original submission did, so a receipt still implies the barrier. |
| The coordinator's NVMe-oF controller is deleted while the owner process and the lease stay valid | The kernel cancels the in-flight command and answers `EIO`. The engine treats `EIO`/`EBADF` as a data break when the pinned controller is verified not live. It evicts the controller and its namespace cache, reconnects through the registry, and rewrites the unadopted suffix. | Same. |
| Same break with a new owner incarnation, a lapsed coordinator lease, or an owner that is not recovery-clean | Fail-stop and reopen, as without the resume. | Same. |
| fsync error | The error is sticky. The frontier fails. Waiters get `FrontierError::Failed`. Completions are refused. The owner must reopen and recover. A retry is never issued, because a failed fsync can drop dirty pages and a later success would not prove durability. The reopened owner is a new incarnation, so it is not continuous. Its recovery makes the adopted suffix durable (restart durability guard): `durable_prefix` keeps an exact prefix. | Same; no receipt for data that may be lost. |
| Owner crash with RF1 | Not tolerated for data on a lost disk. RF1 is one durable owner, not failover. | Same. |

Neither tier provides cross-batch transactions or failover.

Write resume (W1). A transient transport break on the leased write path is not a database failure. The coordinator keeps the frame bytes that it submitted and the owner did not adopt. The bound is two write windows, with a hard cap of 64 MiB for each owner worker. The coordinator reconnects the control session on the same authenticated route. It asks the owner how far each open extent is adopted. It rewrites only the missing frames in ascending offset order. Then it declares adoption again. It refuses in three cases: the owner reports a different incarnation, the lease has lapsed, or the owner is not recovery-clean. In each case the in-memory adoption prefix no longer describes the file. One budget bounds the whole episode: two of the write path's own I/O deadlines, capped by the coordinator lease's deadline. Every probe, declaration, queue open and rewritten frame runs inside it. The code rechecks the lease and the budget before the resume reports success. A deadline is a probe, not a verdict. The resume first keeps the live queue and grants the outstanding work one more window. It escalates to detaching the queue and rewriting only when that window passes with no completion at all. A failed namespace flush is classified by its errno. `ENOSPC`, `EFBIG` and `EINVAL` fail the database on the first report. `EIO` and `EBADF` are ambiguous. They resume only when the engine proves that the pinned controller is not live: its `state` is not `live`, its sysfs entry vanished or was reused, or its namespace node is gone. Otherwise they are the media verdict and fail the database. A target rejection such as `EREMOTEIO` always fails the database. On a data break the pool evicts the lost controller and clears its namespace cache before the resume opens a queue, so the reconnect goes through the connection registry and creates a new controller. The engine requests `keep_alive_tmo=5` and records it in the route evidence. Reads use the same controller pool, so a read grant shares its subsystem's controller with the write path. A read that fails with `EIO`/`EBADF` resumes when the pinned controller is verifiably not live: the lane evicts the dead lease, reconnects, and retries the members inside the read's own deadline. One reconnect is allowed for each request, and a second lost controller returns a transient error to the caller. A caller-inline read never sets up a controller, so it declines the member to the lane instead of poisoning the read authority. `EIO` with a live controller and `EREMOTEIO` still fail the database. A namespace open or verify that reports a controller which is not live is the same resumable class: the engine types the cause, not the message. A refused `delete_controller` store on a controller that is already deleting counts as a teardown in progress, and the engine then waits for the removal. The eviction retires only an entry whose lease is verifiably not live, it evicts only the subsystem of the queue that broke, and it uses the connect window as its own bound. A lost inline read declines the member to the lane instead of failing the read authority. A lost controller resumes like a lost write. A detached queue that the database's reaper cannot accept (capacity or stopped) is a fail-stop, not a break. The queue is parked for the shutdown drain instead of being dropped on the worker thread. The retained budget is admission backpressure. A submission above it is deferred, never queued. Counters: `resume_attempts`, `resume_rewrites`, `resume_frames`, `resume_refused`. A database that fail-stops with `owner <p> restarted` or `coordinator lease lapsed on owner partition <p>` needs a reopen. A database that fail-stops with `live_resume` twice in a row needs the link checked.

## Runbook: permanent loss of one owner disk (RF1)

Permanent loss of one owner disk under RF1 is equivalent to the loss of the disk of a single Tidehunter database. RF1 has one durable owner and no failover. No other owner holds a copy of the data on the lost disk. Do these steps:

1. Stop the database.
2. Restore the validator from a Sui snapshot.
3. Reopen the database.

Partial rebuild of one owner is not supported. Do not try to rebuild only the lost owner.

## Counters (`Frontier::stats`)

Lag between appended and synced is unbounded by design under the native cadence. Monitor it. The lag counters are `lag_bytes`, `lag_batches`, `lag_age` now, and `peak_lag_*` at the start of any fsync.
The syncer counters are `fsync_calls`, `fsync_failures`, `fsync_bytes`, `fsync_batches`, `max_batches_per_fsync` and `batches_per_fsync()`.
The wait counters show waits that blocked, with the blocked time: `appended_waits`, `synced_waits`, `flush_requests`, `flush_waits`, `flush_wait_ns`, `flush_wait_max_ns`.
The completion buffer counters are `pending_completions`, `peak_pending_completions` and `completion_full_waits`.
`lag_age` of the oldest unsynced position overestimates the age of positions appended during an fsync. Those positions count from the fsync start. Use `peak_lag_*` and `lag_*` to see whether the triggers keep up. Nothing in this module limits lag.

## Bounds and queues

| Item | Owner | Capacity | Full policy | Shutdown |
|---|---|---|---|---|
| Out-of-order completion buffer | `Frontier` | `max_pending_completions` (default 4096, 24 bytes each) | wait; the completion at the frontier never needs a slot, so the lowest unfinished writer always progresses | `stop`/`fail` wake blocked writers with an error |
| Waiters | condition variables | one per caller thread | not queued per request | `stop` releases waiters that cannot be satisfied (`Stopped`) |
| Syncer | one thread per owner | one fsync in flight | later completions join the next fsync | `Syncer::shutdown`/drop: stop, one final fsync of the appended frontier, join |
| Durable-cut inbox (reports, flush certifications, stop) | actor `value-wal-durable-cut` | owners + 8 messages; at most `owners + 8` drained per evaluation | senders wait; no sender holds a lock | sent `Stop` after every poller joined; exits on it or on disconnect |
| Durable-cut pollers | one thread per owner | one long poll in flight per owner | not queued | stop channel (`try_send`) and stop eventfd (level-triggered, never drained), join; a parked poll returns immediately |
| Lag samples | actor | 256 | the newest sample absorbs new floors and keeps its time (age only overestimated) | dropped with the actor |

Locking. One `parking_lot::Mutex` for each frontier (one for each owner WAL, so the lock is sharded by owner). The lock has no I/O and no allocation inside it, and it is the only lock in the module. The fsync callback runs with it released. The frontiers are also mirrored in two atomics for lock-free reads.

## Residual serialization

* One mutex for each owner is taken by each completion, wait, and syncer capture. The critical sections are a few loads and stores. The owner append is already serialized under the partition state lock. This mutex therefore adds no new contention domain. [INFERENCE: not measured; no benchmark was run.]
* One syncer thread for each owner WAL: at most one fsync in flight for each owner. A Synchronous acknowledgement that arrives during an fsync waits for that fsync and for the next one. With no fsync stall that is about two fsync times. A stalled fsync delays every waiter that follows it without limit. More fsync parallelism for each owner needs a different WAL layout, not this module.
* A Synchronous acknowledgement waits for the contiguous predecessors to complete first (the frontier is contiguous). A Native acknowledgement waits for the same predecessors, but not for any fsync.
* Different owners sync in parallel. `flush_all` takes the slowest owner, not the sum.

## Benchmark pairing

Compare each tier only with its cohort. Never rank across cohorts.

* `native` with the native `page_cache` cohort (`native_pagecache`; the `native_async_write` pure-write cohort uses the same `page_cache` boundary). Distributed `native` still adds the owner hop, so it is not a no-network equivalent.
* `synchronous` with native `value_wal_barrier` and Valkey `appendfsync always`.
* State the tier next to every number. The harness refuses a run whose backend receipt `configuration.durability_tier` differs from the requested tier.
