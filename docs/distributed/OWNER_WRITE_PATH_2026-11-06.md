# Owner write path: conflict index, group commit, live grouping

Scope: owner append, owner persistence, coordinator publication admission, live NVMe-oF writes. Evidence that motivated it: one benchmark repetition of the 6 Nov 2026 campaign (1 KiB, c16): owner conflict lookup mean 38.5 us against a 4.7 us WAL copy; one flusher command at a time; one unresolved live reservation with persistence inline in the single control actor. One repetition gives no significance; the numbers below that are predictions are marked [INFERENCE].

## 1. Conflict lookup (`reference_directory.rs`, `storage.rs`)

`append_group_impl` checks every batch for a repeated identity (exact retry or `IdentityConflict`) and for a reused version (`VersionConflict`) under the partition `state` lock.

* **Pending entries** (at most 1,024, not yet spilled): two open-addressed tables of `u16` positions, one keyed by identity, one by version. Probe loops are bounded by the table size. The tables are rebuilt when a prefix is adopted into history (once per spill). The hash is seeded per directory, so clients that choose identities cannot force long probe chains. Cost per lookup is O(1) expected, independent of the pending length; the previous cost was a linear scan of every pending entry, twice per batch.
* **Rooted history** (on disk): a seeded Bloom filter over every identity and version ever published to this directory. It never forgets a key, so "absent" is exact and skips a Patricia-tree read; "maybe present" reads the tree as before, so every answer is exact. The filter stops filtering (always "maybe") once it holds more than a quarter of its capacity in keys. It exists only when the history was empty at open; a recovered directory reads the tree for every non-pending key. Its size is charged against `max_reference_metadata_bytes` at open (1/128 of the budget headroom per filter, at most 256 KiB, none below 2 KiB).
* `lookup_conflict` answers identity then version under **one** authority read guard and keeps the old precedence: a rooted identity match wins over a pending version match.
* Counters (`StorageWriteProfile`): `append_conflict_lookups`, `append_conflict_pending_probes`, `append_conflict_history_lookups`, `append_conflict_filter_skips`.

[INFERENCE] The removable part of the 38.5 us is the pending scan plus the rooted-tree reads for absent keys; the measured split was not collected, so the counters above must be read in the next run before claiming a gain.

## 2. Publication admission (`remote_db.rs`)

`admit_prepared_with_progress` grew every outstanding publication-view reservation under the exclusive index guard, scanning all submissions twice. Each admission reserves exactly its own exclusion capacity `n` (the number of outstanding submissions at admission) and grows every older live reservation to at least `n`, so capacity never increases from the oldest live reservation to the newest. It now makes **one** newest-first pass that stops at the first reservation that already fits, sums the additional charge **before** the index writer handle is taken, and holds the handle only for the capacity check and the growth. The handle (`NativeIndex::writer`) excludes only other index writers (publication, checkpoint capture), never readers.

Honest bound: while the window grows (nothing published) every older reservation needs `+1` slot per admission, so the pass is O(live reservations) with one retention-mutex operation each; it is O(1) only when `n` did not grow (a steady window). Reaching O(1) for a growing window needs an aggregate quota hold with lazy growth at consumption, which changes the retention accounting API; it is not done here. A reader pin may take quota between the preflight and the growth; the growth then fails with `Capacity` before any WAL effect. Pinned-view exclusions, dependency predecessors and clock allocation are unchanged.

Counters (`AuthorityWriteStats`): `admission_view_scanned`, `admission_view_grown`, `admission_exclusive_lock_ns`, `admission_exclusive_lock_max_ns`.

## 3. Group commit and owner concurrency (`tcp/control.rs`, `storage.rs`)

* A fixed pool of 4 control workers drains the bounded control queue. Append, live reserve and live completion overlap (the partition state lock orders WAL allocation); every other control is an exclusive barrier that waits for earlier appends to reach the flusher and holds back later commands. The node inventory lock covers only the active-log lookup, not the append.
* Each log has one `Frontier` and one syncer thread (`durability/frontier.rs`), created on its first append. Appends publish `publish_appended(group_end)` under the state lock, so the frontier follows WAL order exactly. The syncer runs `PartitionLog::sync_for_frontier` = `persist_appended`: one barrier for everything appended when it captures the frontier.
* **Native tier**: the worker replies right after the append (or live validation). **Synchronous tier**: the single flusher thread takes the first queued command, then every command that is *ready now* (`try_recv`, never a timer), up to 64 commands or 64 MiB, then waits once on the log's synced frontier and replies to all of them. An empty queue adds no delay; a command's wait is bounded by one sync.
* Every non-append control flushes all logs (`flush_all`: each log's sync is requested before any is awaited) before it runs.

**Crash consistency.** A receipt in the synchronous tier is sent only after `Frontier::wait_synced(end)` returned, and the syncer publishes the synced frontier only after its barrier returned `Ok`; `end` is read from the appended frontier after this command's own group was published, so the barrier that satisfies it covers the group. A failed barrier fails the frontier, every waiter, and every later append; no receipt is returned for bytes that may be lost. The barrier itself is the existing `persist_scope` sequence (WAL file sync, namespace sync for a new file, inventory witness, live frontier root) and is unchanged. Concurrent appends can only raise the captured frontier; the persisted `durable_end` is monotonic and set only after the barrier.

Counters: `persist_barriers` and `persist_barrier_receipts` (receipts per sync), `flush_batches` and `flush_batch_commands` (queued commands per barrier), all in `StorageWriteProfile`; frontier-level counters are in `FrontierStats`.

## 4. Live writes

See `experiments/nvmeof/LIVE_WAL.md`: tiers on the live path, the replay rule beyond the root, the argument that no acknowledged frame lies behind a hole, and merged reservations. The opt-in `leased` write mode (section "Leased extents" of that document) removes the reserve and complete exchanges from the acknowledgement path: the owner leases the rest of a fragment once, the coordinator writes frames with one NVMe write each (FUA in the synchronous tier) and acknowledges on its own completion, and the owner adopts the frames asynchronously. It is not hardware-qualified; `reserved` stays the default.

Higher-epoch live fencing first validates the new authority, invalidates the old reader authority, synchronously revokes/drains target bindings, and releases live pins. Before reopening the old WAL for sealed recovery, it removes only that WAL's syncer slot by `Arc` identity, releases the slot-registry lock, then stops, drains and joins the syncer. This releases both the slot's log handle and the sync callback's handle; flushing the frontier alone does not release either. The existing exclusive-handle check and partition `DbLock` remain required. A drain failure poisons the owner and stops recovery; target revocation or an outstanding external handle also prevents the new authority from becoming active. Same-epoch and invalid fences do not retire the current worker. Retiring the last worker does not permit a durability-tier change after writes began.

An incomplete external frame has a separate in-memory poison cause from a fatal writer/persistence failure. Both reject new writes. Only the known-incomplete cause permits `PersistScope::Appended` to sync the previously validated contiguous prefix, including during the fence's preliminary flush or the syncer's final drain. The incomplete allocation is neither published nor covered by that prefix's live frontier root. Fatal poison and history-background failure are checked before and after I/O and remain fail-stop; an incomplete-frame result cannot clear them. This distinction is not persisted and changes no WAL format.

The recoverable fence regression reserves the absent frame directly at the storage boundary after a native ACK, so the prior valid prefix is deterministically unsynced. This models the real overlap where a reserve worker's preliminary flush finishes before a concurrent completion publishes that prefix. The higher fence must wait for a paused prefix sync, then recover exactly the acknowledged data. `storage/tests/live_native.rs` also covers final syncer drain and fatal persistence/poison dominance before and during I/O.

The `tcp/control_tests.rs::live_fencing` regressions use real WAL files and the unprivileged target-journal fixture for normal and recoverable higher-epoch transitions, exact recovered values, native ACK before sync, no-op fences, and outstanding-handle rejection. The fixture does not prove kernel/SPDK target I/O drain; that requires the live qualification.

## 5. Residual serialization

* **Partition state lock**: WAL allocation, copy, authority publication and the frontier publish are ordered by one lock per partition. The copy is 4.7 us for 1 KiB; it is not parallel across appends to the same partition. Parallel copy needs in-order authority publication (the directory requires strictly increasing offsets) and a hole policy for a failed copy.
* **One unresolved live reservation per stream.** Several outstanding reservations need a client transport that allows several control exchanges in flight and a durable skip record for an abandoned reservation (a format change). Merging queued groups removes most of the per-group cost without either.
* **Coordinator write owner thread** (`remote_db/concurrent.rs`): logical version allocation, dependency tracking and publication stay in one thread. Version order and the contiguous publication prefix are inherent to the design; encoding and hashing (`CompleteBatch::new`) bind the version into the batch, so they cannot move to callers before admission, and a rejected admission must not advance the clock. Per-owner client workers and per-owner append queues already run in parallel.
* **Syncer and flusher** are single background threads per log and per node, off the request path. The synchronous tier adds one thread hop (flusher to syncer) per sync compared with calling the barrier directly. [INFERENCE] a few tens of microseconds; not measured.
* **Recovered directories** have no history key filter.
